# Particle Filter benchmarks

A reproducible way to measure what Particle Filter costs and what it saves: overhead when installed but
inactive, the effect of global and zone filtering, how both scale with particle load, rule and zone count,
and how it compares with other particle-control mods doing the same job.

> **Status: groundwork only. No performance results exist yet.** This directory has the plan, the
> analysis tools, a pilot that checked the measurement pipeline on a frame-capped title screen, the
> synthetic harness (NeoForge 1.21.1 and Forge 1.20.1), the analysis pipeline from harness runs to `compare.py`,
> and the publication tools that archive raw data and rebuild reports from it. So far all of it has only passed
> functional checks and unit tests on synthetic data. Don't quote anything here as a Particle Filter performance
> figure. Performance runs are **blocked** until the owner confirms the laptop's power-limit problems are fixed.
> Start with [HANDOFF.md](HANDOFF.md); to reproduce or audit, [REPRODUCING.md](REPRODUCING.md) and
> [AUDIT.md](AUDIT.md).

The benchmark code and documents were written by Claude (AI), like the mod itself. The owner reviews the
design and decides which campaigns run.

## Tools

| Script | Purpose |
|---|---|
| `tools/frametimes.py summarize LOG [--skip-seconds S] [--duration-seconds D] [--cap-fps N] [--json OUT]` | Metrics and sanity checks for one MangoHud CSV or harness frame log (`.gz` works too) |
| `tools/compare.py CAMPAIGN --reference B [--margin-pct 1]` | Paired comparison of configurations within each stratum, with bootstrap intervals and verdicts; rejects pairs whose per-tick workload or environment differs; keeps the primary 20-TPS dataset, the reduced-TPS saturation dataset and each CPU-/GPU-bound label apart (PLAN.md §4, §5); lists every pair, the pairs where filtering held 20 TPS and the reference didn't (and the reverse), order balance, every run and every exclusion. Refuses functional runs unless `--allow-functional` |
| `tools/ingest_harness.py RUN_DIR... --campaign DIR [--block N]` | Harness launch → one `run.json` + `summary.json` per measured window (achieved TPS and class, workload per tick and per second, diagnostics, sampler and GC-log summaries, bound label, environment, provenance) |
| `tools/system_data.py` | Library: aligns a launch's sampler rows and GC pauses with the harness's windows, the CPU-/GPU-bound label, the power state from snapshots |
| `tools/schedule.py --configs A B C D --blocks 8 --seed N` | Counterbalanced (Williams design) run order |
| `tools/collect_env.py --out env.json [--instance DIR] [--java PATH] [--pid PID]` | Hardware, software, display, power and mod-list snapshot (read-only; home paths and serials left out). `pfbench.py` runs it before and after every launch |
| `tools/sample_system.py --pid PID --out-dir DIR` | Per-thread CPU (and which core), clocks, temperature, RSS, `nvidia-smi` GPU stats during a run, stamped with CLOCK_MONOTONIC. `pfbench.py` runs it for every launch. Don't use `--self-cpu`: the owner prohibits changing CPU affinity |
| `tools/make_pf_config.py synthetic\|miss\|rules\|zones` | Particle Filter configs for the benchmark configurations |
| `tools/pilot_devclient.sh OUT [WARMUP] [DURATION] [--hide]` | Pipeline pilot: dev client under MangoHud on the title screen |
| `harness/pfbench.py template\|run\|campaign\|check` | Synthetic harness launcher: template world, one launch per configuration set, counterbalanced campaigns (`--dry-run`: order, pairability, balance, duration), functional checks ([harness/README.md](harness/README.md)) |
| `tools/publish_campaign.py archive\|report\|manifest\|verify` | Raw launches into a campaign directory; rebuild `runs/`, `comparison.*` and `report.generated.md` from raw data alone; `SHA256SUMS`; check hashes and rebuild byte for byte ([REPRODUCING.md](REPRODUCING.md) §8) |

Tests: `python3 -m unittest discover -s benchmarks/tools/tests -v` (run from the repository root).

## Data layout

```
results/<campaign>/                  (AUDIT.md §1)
  PREREGISTRATION.txt                campaign --dry-run output + analysis arguments, committed before the first launch
  raw/<run-id>/                      each launch byte for byte (publish_campaign.py archive): frames.csv, ticks.csv,
                                     phases.csv, plan/launch/harness/check.json, env-before/after.json, system/,
                                     game/gc.log, game/logs/, gradle.log, inputs*/; failed launches too
  ARCHIVE.json                       what was copied; SHA-256 of what was left out (world copy, mod jars, screenshots)
  runs/<run-id>--<phase>/            derived per window: run.json (templates/run.json), summary.json
  comparison.md, comparison.csv      compare.py output
  report.generated.md, report-args.json   generated report and the arguments that rebuild it
  report.md                          hand-written interpretation (templates/report.md), quoting comparison.md only
  SHA256SUMS                         every file above
```

Raw data is never edited or deleted. Everything derived is rebuilt from `raw/` by `publish_campaign.py report`, and
`verify` checks that the published files match a rebuild. Bad windows are excluded by the automatic checks or a
reason written in `run.json` before the comparison, and stay listed in every report. Files in `raw/` can contain
local paths (`archive` lists them): review them before publishing. Large `raw/` directories can be published as a
release archive; `SHA256SUMS` still pins them.

## What this suite will not do

- Change Particle Filter's production code, a Minecraft installation, or a world. Benchmarks run in the
  repo's dev client or in copies.
- Publish claims before a campaign is complete and reviewed. Equivalent, inconclusive and negative results
  are reported the same way as positive ones.
